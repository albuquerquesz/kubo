## O que é

O **layout** define em que pasta cada app (`web`, `server`, `native`…) e cada pacote (`db`, `auth`, `ui`…) é gerado. Ele é formado por:

- um **preset**: `standard` (padrão — `apps/` e `packages/`) ou `libs` (`apps/` e `libs/`);
- **pastas de convenção** (`dirs`): onde ficam os apps e os pacotes; `.` significa a raiz do projeto;
- **exceções** por app ou pacote: um caminho específico para um item (por exemplo, o app web na raiz);
- um **escopo** opcional (`scope`) para o nome dos pacotes do workspace: com `"scope": "@acme"`, os pacotes viram `@acme/ui`, `@acme/env`… Sem escopo, o padrão continua `@<nome-do-projeto>`.

Os imports entre pacotes usam o nome do pacote (`@meu-app/ui`, ou `@acme/ui` com escopo), então o código não muda quando as pastas mudam. Paths de `tsconfig`, `.env`, workspaces, Docker e deploy são gerados a partir do layout.

O layout padrão (`standard`) gera exatamente a mesma estrutura de antes — nada muda para quem não usa a opção.

## No site

No [Stack Builder](/new), o botão **Layout** (abaixo de **Templates**) abre a lista de layouts prontos:

- **Padrão**: `apps/` e `packages/`;
- **Libs**: `apps/` e `libs/`;
- **Cliente e servidor**: o front em `apps/client`, ao lado de `apps/server`;
- **Tudo em src/**: `src/apps/` e `src/packages/`.

Escolha um e clique em **Usar layout**. O layout em uso aparece marcado como **Atual**. O comando copiado (`--layout ...`), a [prévia](/new/preview) e o link de compartilhamento passam a usar o layout escolhido. Para combinações que não estão na lista, use `--layout` direto no CLI.

## Aplicar no CLI

Direto, sem conta:

```bash
kubojs my-app --yes --layout libs
kubojs my-app --yes --layout '{"preset":"libs","apps":{"web":"web"}}'
kubojs my-app --yes --layout '{"scope":"@acme"}'
```

Também existe `--layout-code <código>`, que aplica um perfil de layout salvo na conta. No momento o site não gera esses códigos, então use `--layout`.

Detalhes das flags em [Opções do CLI](/docs/cli/options#--layout-presetjson).

## Limites

- Vale para **novos projetos**. Projetos existentes não são migrados nem têm arquivos movidos; o `kubo add` respeita o layout gravado em `kubo.config.ts`.
- Os IDs são fixos: apps `web`, `server`, `native`, `desktop`, `docs`, `api`; pacotes `db`, `auth`, `backend`, `config`, `env`, `infra`, `ui`, `storage`, `api`, `payments`, `email` e os pacotes de integração (ex.: `millionsend`).
- O escopo muda só o prefixo (`@acme/ui`); o nome de cada pacote (`ui`, `env`…) é fixo. O `package.json` da raiz continua com o nome do projeto.

## Para mantenedores do site

O login usa Better Auth + Convex. Configuração necessária (valores ficam no Convex/Vercel, nunca no repositório):

- **Convex** (`bunx convex env set ...`): `SITE_URL` (ex.: `https://kubojs.dev`), `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `RESEND_API_KEY`, `EMAIL_FROM`.
- **Vercel**: `NEXT_PUBLIC_CONVEX_URL` e `NEXT_PUBLIC_CONVEX_SITE_URL` da deployment Convex correspondente.
- **Google OAuth**: callback autorizado `https://<seu-domínio>/api/auth/callback/google` (e `http://localhost:3333/api/auth/callback/google` para dev).
- Ordem de deploy: publique as funções Convex (`bunx convex deploy`) antes do site, para o site não chamar funções inexistentes.
